最近在做制造场景的优化 Agent 研究，我把关注点放到了模型的连续修改上。一个优化问题建好以后，后续还会收到新的要求。每次修改都得接着已有模型往下做，之前仍然有效的规则也要保留下来。

这件事很容易被单次任务的结果掩盖。给 Agent 一段需求，让它生成模型并调用求解器，能得到可行方案，已经能说明一些能力。连续修改又多了一层要求。第十次更新之后，第一次加入的规则是否还在生效？

## 一条新要求会影响哪里

可以用一个简化的排产情形说明这个问题。假设某道工序原来可以交给两台机器，现在其中一台停机。模型需要收缩可选机器的范围，已有安排也得重新检查。如果工序换到另一台机器后加工时间发生变化，后续工序的开始时间还会受到影响。这只是说明问题的假设例子，不对应具体工厂或实验结果。

业务上是一条停机通知，数学模型里却有几处相关内容。Agent 要理解这次变化的含义，也要找到受影响的部分。只改到最显眼的位置，可能留下前后不一致的安排。

与此同时，修改范围也得有边界。新要求没有涉及的交期与工序先后关系，应当继续有效。重新生成整个模型时，这些内容同样需要逐项核对。

## 求解成功以后，还要检查规则

求解器会认真求解交给它的模型。如果 Agent 漏掉了一条工序先后约束，求解器仍可能返回一个可行解，甚至得到更好的目标值。这个结果满足的是修改后的数学表达，和业务原本要求的关系还需要另外检查。

近期研究中，我已经遇到过候选模型保留了原有组件名称，却省略了部分依赖关系的情况。只看名称，模型似乎完整；检查内容以后，才能发现规则发生了变化。独立检查拒绝了这次候选修改，系统继续保留此前接受的模型。

这类检查值得单独做。生成模型的 Agent 已经形成了自己的理解，再让它读一遍并解释，容易沿用同一套假设。检查过程需要有独立依据，例如原始要求和已经接受的规则。能够形式化检查的部分，就交给明确的检查程序。

## 把每次修改当成一个候选版本

我目前探索的思路，是先明确新要求允许改动哪些内容，再围绕这些内容生成候选版本。候选通过检查后，才成为下一轮修改的起点。发现问题时，上一版仍然保留，后续可以针对失败原因继续处理。

这种方式也有成本。局部修改需要理解模型内部的关联，漏掉关联就可能漏改。整体重建可以重新组织模型，却要检查更多内容。哪种方式更可靠，需要在相同的变化序列上比较，也要考虑模型规模和累计修改次数。

因此，我暂时把增量修改看作一条需要验证的研究路线。它能否减少错误，哪些情况下值得使用，都应当由比较结果回答。

## 连续修改需要连续评价

评测这类 Agent 时，我更关心它沿着同一条变化序列走了多远。每一步都应从自己的实际模型状态继续修改，才能看到早期错误怎样影响后续结果。

如果每轮都重新给一个正确模型，任务会容易许多，之前的失败也被清除了。这样的测试可以研究单步修改能力，连续维护的结论还需要另一组证据。

评价指标也需要保留过程信息。最终目标值能反映方案质量，第一次出错的位置则说明模型从哪一步开始失去可靠性。检查拦住了多少错误、被拒绝后能否恢复，都会影响这个 Agent 是否适合长期使用。

目前这项研究仍在推进。我希望逐步弄清楚，Agent 在持续变化的要求下，能够保留多久的正确状态，以及人需要在什么地方介入。对一个每天都要调整的排产模型来说，这些问题直接影响下一次修改能否继续建立在可信的基础上。
