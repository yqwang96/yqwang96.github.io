In my recent research on optimization agents for manufacturing, I have been focusing on successive model updates. Once an optimization model is built, new requirements keep arriving. Each update has to work with the existing model and preserve rules that still apply.

A single-task evaluation can hide this difficulty. An agent that generates a model from a description and obtains a feasible solution demonstrates useful abilities. Repeated updates introduce another question. After the tenth change, does the rule introduced in the first update still hold?

## Where does a new requirement take effect?

Consider a simplified scheduling example. An operation can run on either of two machines, and one machine becomes unavailable. The model needs to narrow the eligible machine set and reconsider the existing assignment. If processing time changes on the remaining machine, the timing of subsequent operations may also be affected. This is a hypothetical illustration, rather than a factory case or an experimental result.

One downtime notice can affect several related parts of a mathematical model. The agent needs to interpret the change and identify its consequences. Updating only the most visible field can leave inconsistent assignments elsewhere.

The scope of the update also needs a boundary. Due dates and precedence rules untouched by the new requirement should remain effective. Regenerating the entire model still requires checking that those rules have survived.

## Check the rules after the solver succeeds

A solver solves the model it receives. If an agent drops a precedence constraint, the solver may still return a feasible solution, perhaps with a better objective value. That solution satisfies the updated mathematical formulation. Its agreement with the intended business requirements needs a separate check.

In recent work, I encountered a candidate model that retained the original component names while omitting some dependency relationships. Checking the names alone would have missed the change. An independent check rejected the candidate, and the system retained the previously accepted model.

Such checks deserve their own role. An agent reviewing its own formulation may carry forward the assumptions that caused the error. Verification needs an independent basis, such as the original requirements and previously accepted rules. Where a property can be checked formally, an explicit checking procedure can help.

## Treat each update as a candidate version

The approach I am exploring first identifies what a new requirement permits the agent to change, then generates a candidate around that scope. The candidate becomes the starting point for the next update only after it passes the checks. If it fails, the previous version remains available while the failure is investigated.

This approach has costs. Local updates require understanding relationships within the model, and missed relationships can lead to incomplete changes. Full regeneration allows the model to be reorganized but increases the amount that needs checking. Comparing the two requires the same sequence of changes, with attention to model size and the number of accumulated updates.

For now, I regard incremental updating as a research direction to test. Whether it reduces errors, and under which conditions it is useful, should be answered through comparison.

## Evaluate the sequence, too

For this kind of agent, I care about how far it progresses through one continuous sequence of changes. Each step should continue from its own actual model state so that an early error can affect later outcomes.

Supplying a correct model at every round makes the task easier and removes earlier failures. That setup can study single-step editing ability. Claims about continuous maintenance require additional evidence.

Evaluation should retain information about the process. The final objective measures solution quality, while the first failure identifies when the model became unreliable. Errors caught by verification and recovery after a rejected update also matter for long-term use.

This research is ongoing. I want to establish how long an agent can maintain a correct state as requirements evolve, and where human intervention is needed. For a scheduling model that changes every day, those questions determine whether the next update can start from a trustworthy version.
